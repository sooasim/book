# 제품 기획서 — 전자책 자동 출판 · 윤문기 통합 시스템 (Ink&Press)

작성일: 2026-06-08
문서 버전: v1.0
대상 독자: 기획자, 개발자, 인계받는 AI 에이전트, 운영자

---

## 1. 한 줄 정의

> **초고(.docx/.md) 한 편을 넣으면, 윤문(다듬기)·전자책 변환·표준 검수·플랫폼별 제출팩 생성·자동 입력 보조까지 한 흐름으로 처리하고, 법적 책임이 따르는 최종 단계만 사람이 확정하는 전자책 제작·출판 운영 시스템.**

## 2. 배경과 문제 정의

기존 `apps/ebook_publisher` MVP는 "이미 완성된 원고"를 14개 국내외 플랫폼에 등록하는 **뒷단(출판)** 을 자동화했다. 그러나 실제 1인 출판/소규모 출판의 병목은 그 앞에 있다.

| 단계 | 현실의 고통 | 기존 MVP | 본 기획 |
|---|---|---|---|
| 1. 원고 다듬기(윤문) | 맞춤법·문체·일관성을 수작업 반복 | 없음 | **신규: 윤문기(Refiner)** |
| 2. 전자책 변환 | DOCX→EPUB 수작업, 깨짐 | 미통합(설계만) | 변환 파이프라인 통합 |
| 3. 표준 검수 | EPUB 오류를 등록 후에 발견 | 미통합 | EPUBCheck/미리보기 자동화 |
| 4. 메타데이터 입력 | 사이트마다 복붙 | 제출팩 생성기 | 윤문 결과에서 메타 자동 추출 |
| 5. 플랫폼 등록 | 14곳 반복 입력 | 반매크로/제출팩 | 그대로 계승 |
| 6. 상태 추적 | 흩어진 메모 | 상태 장부 CSV | 그대로 계승 |

**핵심 추가 가치는 1번 "윤문기"** 다. 윤문기가 원고 품질과 일관성을 끌어올리고, 그 산출물에서 제목·소개문·키워드·목차 같은 메타데이터를 자동 추출해 뒷단 출판으로 매끄럽게 연결한다.

## 3. 제품 목표

1. **하나의 입력, 여러 산출물**: 원고와 메타데이터를 한 번 입력하면 윤문본·EPUB·PDF·플랫폼별 제출팩이 나온다.
2. **사람 중심 안전 설계**: 의미를 바꾸는 윤문 제안과 법적 책임 단계는 사람이 수락/확정한다.
3. **재현 가능·추적 가능**: 모든 변경은 diff와 근거로 기록되고, 출판 상태는 장부에 누적된다.
4. **로컬 우선**: 원고는 저작물이므로 기본은 로컬에서 처리한다. 외부 LLM 사용은 선택·옵트인.
5. **인계 가능**: 다른 AI 에이전트가 작업지시서와 JSON 작업팩으로 그대로 이어받는다.

### 비목표 (Non-Goals)
- 약관을 우회하는 완전 무인 자동가입/무인 최종 출판.
- 사람 확인 없이 원문 의미를 바꾸는 자동 재집필.
- 본인인증·CAPTCHA·세금/정산 자동 우회.

## 4. 사용자 유형과 가치

| 사용자 | 핵심 작업 | 시스템이 주는 것 |
|---|---|---|
| 1인 저자 | 초고 작성 후 출판 | 윤문 + 변환 + 등록을 버튼 몇 개로 |
| 소규모 출판 담당자 | 다수 원고 처리 | 일관된 문체/표기 규칙, 배치 처리 |
| 검수자/법무 | 품질·정책 확인 | 윤문 diff, AI 고지/독점 충돌 게이트 |
| 인계 AI 에이전트 | 자동 작업 수행 | 작업지시서·JSON 작업팩·상태 장부 |

## 5. 핵심 사용자 시나리오

### 시나리오 A — 초고에서 판매까지(해피 패스)
1. 저자가 `manuscript.docx`를 프로젝트에 넣는다.
2. **윤문기**가 맞춤법·문체·일관성·가독성 교정안을 diff로 제시한다.
3. 저자가 카테고리별로 일괄/개별 수락한다(거절·되돌리기 가능).
4. 시스템이 윤문본에서 제목·소개문·키워드·목차 후보를 추출해 메타데이터를 채운다.
5. **변환기**가 EPUB/PDF를 생성하고 **검수기**가 EPUBCheck/미리보기로 검증한다.
6. **출판기**가 14개 플랫폼별 제출팩과 자동 입력 JSON을 만든다.
7. 사람이 플랫폼별 최종 검수 후 직접 제출한다. 상태가 장부에 기록된다.

### 시나리오 B — 윤문만 사용
교정·문체 통일만 필요할 때, 윤문본과 변경 리포트만 산출하고 종료.

### 시나리오 C — 시리즈 일관성
같은 시리즈 여러 권에 공통 용어사전/문체 프로파일을 적용해 표기를 통일.

### 시나리오 D — 기존 MVP 그대로
이미 완성된 원고는 윤문을 건너뛰고 바로 출판 파이프라인으로 진입.

## 6. 기능 범위 (MoSCoW)

### Must
- 윤문기: 맞춤법/띄어쓰기/문장부호, 문체 일관화, 용어 일관성, diff 기반 수락/거절.
- 메타데이터 자동 추출(제목/소개문 후보/키워드/목차).
- DOCX/MD → EPUB 변환(Pandoc), EPUBCheck 검수.
- 기존 제출팩 생성기·상태 장부 계승, 14개 플랫폼 레지스트리.

### Should
- 가독성 분석(문장 길이, 수동태, 반복어), PDF 출력.
- 표지 리사이즈/규격 검사, 플랫폼별 소개문 문체 변환.
- 로컬 LLM(옵트인)으로 문장 다듬기 제안 강화.

### Could
- 시리즈 일괄 관리, 가격 통화 자동 환산, 판매 URL 수집.
- 광고 문구/카피 생성, 개정판 업로드 관리.

### Won't (이번 범위 밖)
- 완전 무인 출판, 자동 계약 체결, 외부 SaaS 상용 결제 연동.

## 7. 차별점

- **윤문 → 출판 일체화**: 교정 도구와 등록 도구가 분리되어 있던 작업을 하나의 데이터 흐름으로.
- **로컬 우선·프라이버시**: 원고를 외부로 보내지 않고도 규칙 기반 + 선택적 로컬 LLM으로 동작.
- **안전 게이트 내장**: AI 고지/독점 충돌/최종 제출을 시스템이 강제로 사람에게 넘긴다.

## 8. 성공 지표 (KPI)

| 지표 | 목표 |
|---|---|
| 초고→제출팩 소요 시간 | 수동 대비 70% 단축 |
| 윤문 제안 수락률 | 60% 이상(과교정 아님의 방증) |
| EPUBCheck 통과율 | 변환본 95% 이상 |
| 등록 후 메타 수정 빈도 | 권당 평균 2회 이하 |
| 인계 성공 | 다른 AI가 작업팩만으로 재현 가능 |

## 9. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 과교정으로 저자 문체 훼손 | 품질 신뢰 하락 | diff·근거 제시, 기본 보수적, 사람 수락 필수 |
| 플랫폼 약관/정책 변경 | 등록 실패 | 레지스트리 분리·버전관리, 사람 최종 확인 |
| AI 콘텐츠 정책 위반 | 계정 제재 | `ai_disclosure` 상태 추적·게이트 |
| 원고 유출 | 저작권/신뢰 | 로컬 우선, 외부 LLM 옵트인·익명화 |
| Windows 의존 | 이식성 | 핵심 로직 Python 표준화, OS별 실행기 분리 |
